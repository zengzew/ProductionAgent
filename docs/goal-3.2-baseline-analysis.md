# Goal 3.2 基线分析

分析日期：2026-08-03

本轮把当前 `content/episode-001/` 与 `content/episode-002/` 视为 v1 基线，只在各自的
`v2-goal3/` 子目录生成新版本。基线判断来自当前仓库文件、现有竖版 MP4 的读回数据和
首帧检查，不把历史报告分数直接当作新版本结论。

## Current architecture summary

ProductionAgent 是以文件为交接面的单 episode 流水线。`research/` 保存 sources、facts
Claim Ledger、事件时间线和产品研究；Story Director、Viral Director、Script Writer、
Oral Rewriter 依次把这些事实变成导演 brief、注意力策略、信息初稿和最终口播。Oral
Judge、Audience Critic、Fact Guardian、Visual Director 与 Retention Critic 通过绑定
SHA-256 的 Markdown gate 审批同一版脚本。通过后，`materialize:story` 生成
`script.json` 与 `narration.txt`，TTS、字幕规划、真实音频时间轴、Remotion 竖版渲染、
输出检查和 Delivery Critic 形成生产与交付谱系。

权威顺序是 research 与 Claim Ledger 决定“能说什么”，director brief 与 viral strategy
决定“先说什么”，final script 决定实际口播，真实 TTS、timeline、SRT 和最终 MP4 决定
交付是否合格。`story/workflow.json` 记录角色、决策、评审轮次和状态；报告中的哈希防止
脚本修改后沿用旧评审。当前实现仍是人工调用这些角色和命令，没有 LangGraph，也没有
外部编排状态。

仓库现有命令只接受单层 `episode-*` ID，渲染入口也只注册 Poke 与 Roost 两个现有
Composition。因此 Goal 3.2 不扩展编排或 Composition 契约。两个嵌套 v2 package 会保留
独立逻辑 episode ID，执行现有 gate 时使用临时兼容别名；别名不承载最终产物。

## V1 baseline

| 指标                 | Episode 001 / Poke | Episode 002 / Roost |
| -------------------- | -----------------: | ------------------: |
| Sources / facts      |            17 / 28 |              9 / 22 |
| 可进入旁白的 claims  |                 21 |                  20 |
| 脚本段数             |                 12 |                  12 |
| 目标时长             |             150 秒 |              180 秒 |
| 旁白字符数           |                761 |                1000 |
| 最终 MP4 读回        |         135.744 秒 |          167.233 秒 |
| 字幕 cues / 微 cue   |             72 / 0 |     87 / 6（6.90%） |
| 当前 Audience Critic |           95 / 100 |            93 / 100 |

两版都已有 Goal 3.0 的关键形式：首帧给动作、前二十秒建立产品心智模型、逐句 Claim
绑定、自然中文口播、视觉方案和成片 gate。首帧检查也确认 Poke 直接展示“消息已发送、
日历已更新”，Roost 直接展示“消息已发送、鸟在路上、预计三天后到达”。因此本轮不能
靠补齐缺失文件或提高自评分来证明改善，必须让同一事实在故事选择、删减和真实成片中
产生可比较的变化。

## Existing quality risks

### Shared risks

- 两个 v1 的评审分数已经很高，分数接近上限，存在 rubric 区分度不足与自证循环风险。
  v2 不能仅把 93 或 95 改成更高分，必须给出可定位的内容差异和最终 MP4 证据。
- 两版都使用十二段结构，部分段落承担的是“资料完整”而非核心问题推进。功能、权限、
  商业和公司事件进入主线后，会稀释人物选择与用户动作。
- 评审报告能验证 schema、哈希和硬门槛，但“显著更好”仍是编辑代理判断。没有发布后
  同平台受众数据，不能承诺真实留存或播放量提升。
- 当前渲染组件固定，v2 可以改变脚本、时长、字幕和镜头内容选择，但不能把组件重做
  当作本目标的质量收益。

### Episode 001

- 前十秒用“一亿条消息”扩大尺度，后段又重复同一数字，信息增量有限。
- 1:48 以后进入持续推理成本和收购，事实成立，但它们对“为什么收起工作台、用户如何
  把产品带出邮箱”只提供旁支，结尾前出现两次换题风险。
- Hook 中“一个小动作，被放大成了一个产品问题”偏编辑概括，不如用户动作本身具体。
- 片中“团队、Beta 用户、公司”都有人类动作，但缺少一条持续跟随的使用体验。人物感
  主要由群体标签承担。

### Episode 002

- 目标时长填到 180 秒，真实成片虽合规，仍达 167.233 秒；十二段和一千字口播让“等
  鸟送信”这个一眼能懂的主意承担了过多解释。
- 1:32 后连续进入 Threads、增长、商店、融资、位置与 Pen Pals。用户仪式感是最强的
  人类故事，却很快被经营与权限信息淹没。
- 商业与权限段有事实价值，但对“等待为什么变成期待”的直接回答较弱，容易形成信息
  完整、故事分散的中后段。
- v1 有 6 条小于一秒的字幕 cue，虽低于 10% blocker，仍增加短促阅读和音画压力。
- 结尾用“慢速社交小赛道的市场信号”作编辑判断，再回到鸟的动作；产品体验的兑现不如
  用户行为本身直接。

## Expected improvement areas

Episode 001 v2 应把主线压回一条可见链：跨应用改日程的麻烦，团队撤掉新工作台并进入
消息列表，Beta 用户把用途推向日常任务，Recipes 把已配置的用法交给别人，公开消息
规模成为这一入口被反复使用的阶段性证据。成本和收购只在确实推进主线时保留，否则从
旁白删除。预期结果是更短、重复数字更少、团队选择与用户动作更连续。

Episode 002 v2 应从“已经在路上的三天消息”直接进入一条有来源的人类故事，把朋友推动
公开、用户用古英语等鸟、地图让等待可见、不同鸟速让等待可玩串成同一条体验链。商业、
融资和非主线权限说明退出旁白，把增长数据放在用户行为之后作为阶段性结果。预期结果是
显著缩短时长、减少功能清单感，并让结尾停在仍在飞向朋友的具体动作。

两版共同使用以下比较标准：前三秒理解速度、二十秒问题清晰度、每二十至四十秒的信息
增量、单一故事问题、产品选择与用户动作的连续性、自然口播、逐句 Claim 保真、字幕微
cue、最终时长与真实证据可读性。独立评审只读取定稿及其上游事实，不修改脚本；v1/v2
比较报告必须同时绑定两版实际 MP4 与 timeline 的 SHA-256。

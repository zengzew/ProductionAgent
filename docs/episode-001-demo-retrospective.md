## 结论

这版已经具备发布候选的核心条件。陌生观众能快速知道画面里发生了什么，前三秒动作、
一亿条消息、运行成本和唯一问题形成连续推进。中段不再按功能或日期罗列，而是沿着
“用户少切窗口，后台却可能多跑很多次”向前走。结尾也回到一次具体的日历操作，没有
转去总结功能或升华行业。

剩余工作不是重写故事，而是修正两个发布前硬问题，再做三项质感微调：

1. 第 0 帧没有出现脚本和 Delivery Critic 所写的消息气泡与日历动作。
2. 字幕生产阶段为了消灭短 cue，重新合并了人工语义 cue，产生了词组和句意断裂。
3. `seg-009` 的信息密度明显高于其他段落，需要人工完整听审。
4. 画面来源栏有不相关或被截断的 publisher，削弱了证据可信度。
5. 全片视觉组件已经有变化，但长时间仍共享同一纸张背景、页眉和卡片语法。

因此，用户所说的“约 90% 可发布”是合理判断；当前不应把自动门禁的 PASS 等同于
所有人工发布条件都已满足。

## 这次真正有效的做法

### 1. Hook 使用四步递进，不靠陌生产品名

本版前 20 秒的顺序是：

1. 一条消息改日历。
2. 约三个月产生一亿多条消息。
3. 创始人承认运行昂贵、很难赚钱。
4. 补出“联系人列表里的 AI 助手”，再提出“为什么越用越贵”。

这套顺序可以复用，但不能机械套数字。核心是先给零背景可懂的动作，再给与动作直接
相关的规模或代价，最后才补产品定义。数字如果不能改变观众对动作的判断，就不应
进入 Hook。

### 2. 全片只追一个问题

旧版容易变成功能目录。发布候选版把邮件、主动提醒、Recipe、消息规模、模型调用和
收购都放回同一个问题：少开界面的便利，为什么会带来持续运行成本。

可复用的故事骨架是：

`具体麻烦 → 团队选择 → 用户如何改写产品 → 可验证使用结果 → 隐藏代价 → 重大转折 → 回到一次具体动作`

它不是固定章节模板。每一段必须回答上一段留下的问题，否则即使事实重要，也只进
画面小字或删除。

### 3. “人物选择”和“用户动作”比功能解释更能推进故事

本版最有效的中段不是 Poke 能做什么，而是两个动作：

- 访谈用户不想再学新界面，团队把工作台收起来。
- Beta 用户开始问天气、球赛和吃药提醒，把邮件助手带出邮箱。

这两步让产品变化有了可复述的原因和承接。下次优先寻找有来源的人物选择、用户动作
和产品改动；找不到时调整故事结构，不用编辑推测补转折。

### 4. 技术只在解释后果时出现

“新邮件一到，自动化就跑一遍；查航班，它得一直刷新”比模型架构说明有效。观众先
看见一次请求，随后看见邮件监听、航班刷新、模型和工具反复调用，技术才真正解释了
成本。

下次判断技术段是否保留，只问一件事：它是否改变用户体验、权限、成本或分发。答案
是否定的，就删掉。

### 5. 事实层和口播层分开，避免研究报告腔

`script-draft.md → final-script.md → oral-review.md → Audience Critic → Fact Guardian`
的分工是有效的。Claim、来源身份、统计期和事实边界留在结构化层，最终口播只保留
观众需要听见的动作和判断。

真正值得复用的是文件职责和哈希绑定，不是本轮 5/5 或 96/100 的分数。任何文字变化
都会让旧评分和旧哈希失效。

### 6. 视觉和声音要跟信息变化走

这版有效的节奏节点包括：

- 日历动作切到一亿消息。
- 三个窗口切到收起工作台。
- Beta 请求穿过邮箱边界。
- Recipe 卡切真实 Release Notes。
- 一条消息展开成持续后台调用。
- 成本脉冲停下，再切收购公告。
- 结尾回到日历错误。

程序生成的提示音、冲击音和低频脉冲没有替资料制造紧张，只强调已经发生的信息变化。
这比持续铺同一种 BGM 更适合当前产品故事。

### 7. 基线版、发布候选版和哈希一起归档

`output/episode-001/iterations/` 保留了基线、发布候选、脚本、字幕、时间轴和对比报告。
这让“变好”可以回到具体版本，而不是依赖记忆。以后每轮重要迭代都应保留：

- MP4、SRT、final script、production timeline；
- 精确 SHA-256；
- 真实时长、字幕数、最短 cue、音频参数；
- 本轮只改变了什么，以及哪些边界仍未验证。

## 发布前必须修正

### P0：第 0 帧仍是空的

当前第 0 帧只有页眉、来源栏和字幕“给一个联系人发句话”。消息气泡从前 10 帧渐入，
日历卡从第 16 帧开始出现。真正的动作要到约 0.5～1 秒才可见。

这与以下 source of truth 冲突：

- `final-script.md`：第一帧即出现消息气泡与移动中的日历卡；
- `delivery-critic-report.md`：第 0 帧出现消息气泡和已更新的日历卡；
- 当前实际 MP4：第 0 帧没有两者。

复用规则：任何“首帧可懂”结论都必须直接解码 MP4 的 frame 0，不能用 Remotion
预览、0.5 秒截图或审片报告代替。Hook 的主动作至少要有一个静态可见状态从 frame 0
开始，后续再做动画。

### P0：字幕语义计划在生产阶段被破坏

`caption-plan.json` 本身保留了语义单元，但 `fitCaptionPartsToDuration()` 为了让每条
字幕不少于 1 秒，只按时长和可见字数合并相邻 cue。结果 SRT 出现：

- cue 37：`随时能叫到的助手 产品的边界`
- cue 44：`草拟回复 省下来的`
- cue 45：`是你来回切窗口的动作 交出去的`
- cue 52：`装进 Recipe 链接 朋友点开`
- cue 59～60：`Apple Messages for` / `Business`

这些 cue 没有拆开英文单词，却拆坏了完整术语、主谓关系或句子边界。自动检查只验证
单词、长度和时长，因此产生了假 PASS。

复用规则：

- 人工 caption plan 的 cue 边界默认是硬边界。
- 短 cue 优先在同一 cue 内换成两行，或调整相邻 cue 的显示时长。
- 只有同一语义组内才允许合并；不能仅凭“合并后少于 16 字”决定。
- Delivery Critic 必须比较最终 SRT 与 caption plan，不能只比较 SRT 与 generated JSON，
  因为两者可能由同一错误步骤生成。
- 专有名词要按完整术语检查，例如 `Apple Messages for Business`，不只检查单个英文词。

## 建议微调

### P1：优先听审 `seg-009`

以去除空白和标点后的字符数除以真实音频时长估算，其他段落约为 4.8～6.1 字符/秒，
`seg-009` 达到约 7.14 字符/秒。它同时承载 3 月开放、6 月 Apple 入口、一亿消息、
统计口径和“一次任务不只一来一回”五层信息。

发布前应完整耳机听审这一段。若出现吞字或观众来不及读画面，优先删减日期口播或将
渠道日期只留在画面，不要整体加长全片。

### P1：修正少数仍偏书面的句子

Oral Judge 的高分说明整体方向正确，但不能代替逐句口播判断。以下句子仍值得微调：

- `Poke 把背景设定、开场白和要连接的服务，装进 Recipe 链接。`
  使用了项目明确要求避免的“把 A、B 和 C 装进 D”结构。
- `产品的边界，就这样被真实请求往外拉。`
  “产品边界”比前面的吃药、天气和球赛更抽象。
- `为什么这个省掉界面的产品，反而越用越贵？`
  “省掉界面”可能被理解为完全没有其他界面；“少切窗口”更贴近已证实范围。

微调时不要改变故事结构，也不要新增 Claim。任何修改后都重新生成 oral review、
Audience Critic、Fact Guardian、TTS、字幕、时间轴和竖版视频。

### P1：让来源栏服务当前画面

当前来源栏机械展示 Claim 绑定的前三个 publisher。开场 `claim-poke-011` 因同时绑定
监管旁证、媒体和官网，frame 0 先显示了意大利竞争监管机构，和“消息改日历”的画面
关系很弱；多个来源名称还因宽度不足被省略。

下次不要把 Claim 的所有来源直接当画面署名。每个镜头选择一条最能支持当前画面或
旁白的来源，完整显示短 publisher，并把详细 URL、交叉核对和次要来源留在 Claim
Ledger 或片尾来源页。

### P2：增加两到三次真正的视觉语法切换

当前联系表、卡片、时间线、调用链和公告截图已经比基线丰富，但全片仍长期共享浅色
纸张背景、上方章节号、右上角来源 badge、下方字幕条。九秒间隔的全片抽帧中，这种
同构非常明显。

下次优先在真正的信息转折处改变构图，而不是增加装饰：

- 真实网页证据可短暂全屏，随后再回到程序化图形。
- 成本段可让后台调用占满纵向空间，减少“标题 + 卡片”版式。
- 收购静音段可保留更长的空白或整屏证据，不急着恢复统一页眉。

## 下次复用的验收顺序

1. 先锁定当前 MP4、SRT、production timeline 和 final script 的哈希。
2. 直接读取 frame 0，再看 0.5、1、3、6、10、15、20 秒。
3. 生成全片等间隔 contact sheet，检查视觉语法是否长期同构。
4. 对比 caption plan 与最终 SRT，逐条检查语义组、主谓关系和完整专有名词。
5. 计算每段真实音频时长和字符密度，把异常段落列为人工听审优先级。
6. 检查每个画面来源是否真的支持当前句子，而不是只看 Claim 是否有来源。
7. 把问题分为发布 blocker、质感微调和发布后验证，不混成一个总分。
8. 修改旁白后，重新走完整文本、TTS、字幕、时间轴、渲染和交付门禁。

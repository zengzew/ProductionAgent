# 技术说明

## 已确认

- Poke 通过既有消息渠道接收请求并主动回复。[claim-poke-010]
- 它能连接邮件、日历和其他服务并执行动作。[claim-poke-011]
- Recipes 把 onboarding context、首条消息、所需集成和分享链接打包。[claim-poke-012]
- Poke 官方文档确认支持 MCP 服务器，可发现并调用外部工具。[claim-poke-012]
- 创始人称系统会按任务选择大型供应商或开源模型。[claim-poke-013]
- Cognition 把双方的共同方向称为 always-on cloud agents。[src-poke-007]

## “为什么是这个时候”的证据边界

资料能确认几块已经可用的能力：

1. 创始人称 Poke 会按任务选择不同模型。[claim-poke-013]
2. 官方产品说明显示，Poke 能在消息渠道中主动联系用户，并在授权后读取邮件、日历和其他服务。[claim-poke-010, claim-poke-011]
3. 官方文档显示，Recipes 能打包所需背景、首条消息和集成设置，Poke 也支持调用 MCP 工具。[claim-poke-012]

这些能力能解释产品在手机上如何工作，也能说明体验、权限、分发和成本发生了什么变化。现有来源没有证明它们在同一时刻成熟，也没有证明其中某一项促成 Poke 的起源、方向变化或增长。Story Architect 只能把“这些组件在 2025 至 2026 年已经可用”写成编辑解释，不能写成已证实的技术突破。

## 与增长和风险的关系

连接邮件和日历让一句请求可以继续变成真实动作。创始人举出的成本例子也很具体：对每封新邮件运行自动化、实时检查航班状态，都会继续产生推理成本。[claim-poke-011, claim-poke-021]

Cognition 把双方的共同方向称为 always-on cloud agents。这是收购方对方向的表述，不能拿来确认 Poke 当前的内部常驻架构。[src-poke-007]

当 agent 能访问邮件、日历和真实动作时，错误输出与隐私策略的后果也比普通聊天更重。[claim-poke-023, claim-poke-024]
